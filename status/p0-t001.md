14. **T-041: "narrow the docstring to what is accepted" needs the acceptance list written from the code, not from the ticket.** My first draft of the URL tests asserted that `parseGitHubUrl` rejects `https://github.com/only-owner` and that it throws the `github.com/owner/repo` hint. Two further notes for whoever reads this later: the second required change, aligning the validator's regex, needed no code change at all, because the validator was already HTTPS-and-github.com-only and the parser was the liar; and the atomicity guard is scoped to the JSDoc above `createNewProject` rather than to the file, because the function *body* legitimately contains the words "does NOT support db.transaction()" — guarding the whole file flagged the truth as the lie.
15. **T-050: a mocked query builder that ignores `limit` makes an over-fetch assertion vacuous.** Both new tests assert `hasMore`, which is derived from a row fetched past the page. The existing `chain()` helper in `issue-comments-ownership.test.ts` self-returned for `limit` like every other method, so it would have handed the service all 60 comments regardless of the page size and the assertion would have passed for a service that never over-fetched. Both builders now honour `limit` and record the values. Two smaller consequences of the same test: `String(sqlCondition)` is `[object Object]`, so the keyset predicate has to be walked through `queryChunks` (recursively — `or()` nests its operands as further SQL objects) for the "cursor is in the same statement as ownership" assertion to see anything; and the "60-comment thread is reachable" test cannot be a real keyset walk, because a builder is not a database. What it does prove is the *cursor contract* — the cursor must name the last row returned, not the overflow row held back, since that is the difference between reaching all 60 and silently losing one per page.
16. **T-051: a `z.string()` where the column is `uuid` is a silent wrong answer, not a crash.** The interesting part of T-051 was what the red run showed rather than what the ticket claimed: a malformed id does not error, it matches nothing and comes back as `NOT_FOUND` — the same response as a file that genuinely does not exist. Nothing in the system was broken-looking, so nothing would have been reported. Worth remembering when auditing input validation: on a typed column, "missing validation" and "missing row" are the same observable event.
