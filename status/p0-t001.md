## Surprises

1. **`@radix-ui/react-select` is imported but not declared.** `src/shared/components/ui/select.tsx:4` imports it; `package.json` listed nine other `@radix-ui/*` packages but not this one, so `bun run typecheck` **and `bun run build`** both failed on a clean checkout. It looked fine in the main worktree only because a stale `node_modules` there happened to contain it. Left alone through T-001/T-003/T-004 as out of scope, then cherry-picked as `5bf6a89` from `batch4-fixes` (`15c3ea2`) because T-009's verification requires `bun run build`. It is the same 2-file, 6-line change that branch already carries, so the eventual integration is a no-op, not a conflict. If `batch4-fixes` lands first, drop this commit.
2. **`.env` is untracked**, so a new worktree starts without it and `db:backup` fails with "DATABASE_URL environment variable is not defined". Copied in manually; it is gitignored and was not committed.
3. The GH Actions half of the acceptance criteria (`gh workflow view/run backup.yml`) cannot be exercised from a feature branch — the cron only fires from the default branch. Post-merge action.
4. `python3 -c "import yaml"` is unavailable on this machine; YAML was validated with `js-yaml` via `bun` instead. Note `workflow_dispatch:` with no value parses as `null`, which is GitHub's "enabled" — do not assert it is truthy.
5. **T-004: the corruption does not always surface where the ticket assumed.** The task describes a corrupt/truncated 200. Truncation is the *benign* case — gunzip still emits the blocks it decoded, `extract` sees a bad header and fails first, and the pre-existing `extract.on("error")` already caught it. The crash only happens when zlib rejects the payload outright (not-gzip, or a mangled deflate body), because then `extract` never receives a byte and never errors. The tests cover all three shapes.
6. **A full `bun run test` flakes on its first run after a file is added.** Cold transform cache: the first run takes ~108s with ~90s in transform, and `clerk-webhook.test.ts` and `project-tabs-aria.test.tsx` fail. Warm runs take ~42s and pass. Confirmed not a regression by stashing the change and running those two files in isolation both with and without it. Rule of thumb: re-run before believing a full-suite failure.
7. **The P0 queue is not unclaimed — other lanes got there first.** At the time I picked T-006 it was already committed on `lane/p0-A` (`d38344f`), and none of those commits are on `main` yet. Mapping found at the time: T-006 → `lane/p0-A`, T-007 → `lane/p0-B` (`de5bf7c`), T-008 + T-010 → `lane/p0-C` (`b6924a6`, `158df20`), T-011 → `lane/p0-A` (`e6000d7`), T-003 done twice (`ac0a564` on `lane/p0-B` and `9c792e7` here), T-001 also recorded on `lane/p2-a` (`a64c010`). T-009 was the only remaining P0 task nobody had taken, which is why I took it. **T-006/T-007/T-008/T-010/T-011 are done but unmerged — integration onto `main` is still owed to a human, and T-003 exists twice.**
8. **T-029: the dashboard's cost is response width, not round-trip count or query plan.** The audit framed this as seven stateless HTTP requests, so the obvious fix is to consolidate them. Measurement says otherwise. `EXPLAIN ANALYZE` on `getRecentActivity`'s SQL is 0.134 ms of database time, and `getCommitChart` (same join, same tables, aggregate instead of rows) runs at the 72 ms network floor. The 475 ms outlier is entirely `commit_message`: full text averaging 1,092 bytes and peaking at 65,536, transferred eight rows at a time over `neon-http`. Swapping that column for `c.id` takes the same query to ~90 ms, and re-adding `author_avatar`, `author_name` or `projects.name` one at a time changes nothing. So whoever does the consolidation should cap `commit_message` on the way out *first* — no merge removes the 64 KB row, and that one query is two thirds of the widget. The mergeability notes are in the comment block at `projectService.ts:495`.
9. **T-030 confirmed T-029 from the other side: the batch helped less than the column would have.** Consolidating ten stateless `neon-http` requests into one `db.batch()` transaction took `getDashboardData` from ~717 ms to ~424 ms median — real, but the ceiling was never round-trips, because `Promise.all` had already overlapped them. Capping `commit_message` was left undone on purpose: it is the only change that attacks the measured 400 ms, and it alters what the widget renders, so it is a product decision rather than a refactor. It is now the obvious next task and the T-029 comment points at it.
